# @lotiai/composer

## 0.5.0

### Minor Changes

- [#19](https://github.com/lotillc/composer/pull/19) [`3f511af`](https://github.com/lotillc/composer/commit/3f511af4968fc9743b8d15e2d9c42d905d413f07) Thanks [@john-goloti](https://github.com/john-goloti)! - Stop leaking raw error text into sinks a consumer cannot redact, and add the seams to control the ones that remain.

  Composer put a step error's message into three sinks without asking the consumer: the injected logger, OpenTelemetry span attributes, and Temporal's event history. For a MikroORM/knex driver error that message is the fully parameter-inlined SQL, quoting real row values.

  - **Failure logs carry the `Error`, not a projection of it.** `endWorkflowObservability` logged `error: { name, message, stack }` and the activity worker logged a bare `error: stepError.message`. Both discarded the structured fields a serializer classifies on -- a pg error's `code`, `severity`, `table`, `constraint` -- and severed the `cause` chain below the top-level wrapper. Composer now hands the logger the `Error` and lets its serializer decide. Swept across every site that logs through the injected `ComposerLogger`. **A logger that `JSON.stringify`s its metadata will now render `error` as `{}`; give it an error serializer.**
  - **Span attributes no longer carry the raw message by default.** `workflow.error.message`, `workflow.batch.error.message` and `step.error.message` are replaced by `*.error.type` (the error's name), and `recordException` receives a name-only exception rather than the `Error` -- whose `stack` header line repeats the message. The span status description is likewise empty unless a message is rendered. Spans keep `*.error.type` and gain `*.error.code` where the error carries a string `code`, so a failure stays identifiable in a trace. The new `createComposer({ traceErrorMessage })` option puts text back on the span, scrubbed or raw as the consumer decides; a renderer that throws falls back to no message rather than replacing the workflow's own error.

  `DataConverter`, `FailureConverter`, `PayloadCodec` and the activity-interceptor types are re-exported from the package entry point, so writing either seam does not require a direct dependency on the Temporal packages.

  - **Log metadata keys renamed at three cleanup sites.** `cleanupError` and `contextError` become `error` (so the line's own error sits under the key a serializer looks at), and `originalStepError` becomes `originalStepErrorName` -- the step error is logged in full elsewhere, and a second copy of its message is a second thing to redact. Alerts keyed on the old names stop matching.
  - **`temporal.dataConverter` and `temporal.interceptors` are now exposed.** A `failureConverterPath` or an activity-inbound interceptor can rewrite a failure before Temporal records it. `dataConverter` reaches both worker types and the client Composer uses to start and await workflows, since a converter installed only on the workers leaves the client unable to decode what they wrote.

- [#20](https://github.com/lotillc/composer/pull/20) [`d042ea6`](https://github.com/lotillc/composer/commit/d042ea64e12026ffe91377ddb3a3ea0b49699665) Thanks [@john-goloti](https://github.com/john-goloti)! - Stop Composer's own error wrappers and Temporal payloads from repeating a wrapped error's message.

  The previous change closed the sinks Composer wrote to on the Node side. Three paths stayed open because each needed a decision: the async path's workflow-side logging, the workflow bag in `ApplicationFailure.details`, and `WorkflowStepError` inlining the original's message. All three are closed here, plus a fourth found while sweeping: FanOut inlined every failed child's message into the error it throws.

  - **A wrapper's message is its own.** `WorkflowStepError`, `WorkflowBatchError` and `WorkflowErrorHandlerFailure` now carry only Composer's context -- which workflow, which step, which batch -- and never the wrapped error's message. **This changes every wrapper error message a consumer sees.** The original is on `.cause` and `.originalError`; `matchesError()` is unaffected. This also removes a trap: a wrapper copies the original's `code` but not `severity`, `table` or `constraint`, so a scrubber that rebuilds a database error's message from structured fields saw a wrapper that looked like the original and passed its inlined SQL through. `toLogContext()` likewise hands over the `Error` itself rather than a `{ name, message, stack }` projection.
  - **Nothing Composer hands Temporal carries an error message.** A step failure travels as `{ stepName, code, parentCodes, type, cause }` at every depth -- **`StepFailureInfo.message` and `SerializedErrorInfo.message` are gone**, from the error-handler activity's argument and from the `ApplicationFailure` details alike, both of which persist in event history. A crashed error handler and a failed FanOut child are likewise named by code, not by message.
  - **The bag is its own details entry.** An unhandled workflow error now throws with `details: [{ error }, { bag }]` instead of `[{ bag, error }]`, so a scrubbing failure converter can drop the bag whole without rebuilding the error beside it. **Read partial workflow state from `details[1].bag`.** Composer's own client reads the new layout and falls back to the old one, so a workflow started by an older bundle still yields its bag.
  - **A code recovered from a `CODE: message` prefix must look like a code.** The prefix is now required to match `[A-Z0-9_]{2,50}`. A bare 50-character cutoff laundered arbitrary message text into `code` -- `constraint "u_email": Key (email)=(jane@x.com)` yielded a 20-character prefix quoting the row -- and `code` is emitted precisely where the message is withheld.
  - **`details[0].stack` carries frames only.** V8 opens a stack with its `name: message` header, so copying `error.stack` whole put a second copy of the message where a converter scrubbing `message` and `stackTrace` would not look.
  - **`Runtime` is re-exported.** Workflow-side `wf.log` lines are routed by Temporal's own `Runtime` logger, not the injected `ComposerLogger`. Composer does not wire the two together: `Runtime.install` is process-global and single-shot, the per-worker alternative is a sink name Temporal reserves, and sink arguments cross the sandbox by `postMessage`, so an `Error` could not arrive intact for a serializer anyway. Composer stops putting raw text in those lines instead, and re-exports `Runtime` for a consumer who wants to route them.

## 0.4.0

### Minor Changes

- [#17](https://github.com/lotillc/composer/pull/17) [`449764f`](https://github.com/lotillc/composer/commit/449764fc3918268ce8494237bec908a781ac349f) Thanks [@john-goloti](https://github.com/john-goloti)! - Add `nonRetryableErrorTypes` to `StepRetryPolicy`, so a step can declare which error codes must not be retried at the Temporal activity boundary. Codes listed in `asyncRetry.nonRetryableErrorTypes` are threaded through the workflow plan into the activity's Temporal `RetryPolicy`, where they are matched against `ApplicationFailure.type` — which the framework already populates from the thrown error's `code`. A step throwing a listed code fails on its first attempt instead of burning the remaining `maximumAttempts` on work that is guaranteed to fail identically (content-policy rejections, validation failures, permanent 4xx responses).

  The field is optional, and when it is unset or empty the retry policy handed to Temporal is unchanged. Errors that are not listed remain retryable.

  Also makes `parentCodes` optional when detecting coded errors at the activity boundary. Previously an error was only converted to a coded `ApplicationFailure` if it carried **both** a string `code` and a `parentCodes` array, so an error with just a `code` reached Temporal with its class name as the failure type and its code lost — which would have silently defeated `nonRetryableErrorTypes` for those errors. Errors carrying a string `code` but no `parentCodes` now get the same treatment as fully coded ones (`parentCodes` defaults to `[]`), which means such an error's `code` — rather than its class name — is now what surfaces in `StepFailureInfo.code` and in workflow error results. Errors with no `code` at all are still passed through untouched, and retryability is unaffected for anything that does not opt in.
